# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Patch Notes Delivered (PND) is a World of Warcraft addon (Lua) that shows official game patch notes and addon changes on login. There is no build step — the addon is plain Lua loaded by the WoW client via the `.toc` file. The repo also contains a Python-based GitHub Actions pipeline that scrapes Blizzard news and uses an LLM (Gemini) to draft patch-notes updates as a PR.

## Repository layout

- `PatchNotesDelivered/PatchNotesDelivered.toc` — addon manifest (interface versions, addon version, load order of libs/notes/core files). Any new Lua file must be added here or it won't load.
- `PatchNotesDelivered/PatchNotesDelivered.lua` — core addon logic: AceAddon init, minimap/data-broker button, options menu, the patch-notes window (`ShowPatchNotes`), slash commands (`/pnd`, `/pnd-mini`).
- `PatchNotesDelivered/PatchNotesWindow.lua` — custom AceGUI container widget (`Window-PND`) that `ShowPatchNotes`/`ShowPatchNotesPopup` build their windows from. Wraps Blizzard's native `ButtonFrameTemplate` (portrait, title, close button, inset content area all supplied by the template) rather than drawing custom chrome; addon-specific glue code, not a vendored library.
- `PatchNotesDelivered/PatchNotesImageWidget.lua` — custom AceGUI leaf widget (`Image-PND`) for rendering a single image inline in the patch-notes window. Sized via caller-supplied width/height (not its own aspect-ratio math) so it lays out correctly inside the same `Flow`-layout `ScrollFrame` as the text `Label` children; `RenderEntryBody` in `PatchNotesDelivered.lua` interleaves it with text wherever a `[[img:N]]` marker appears — see the `images` field below.
- `PatchNotesDelivered/PatchNotesText.lua` — `AVAILABLE_NOTES` registry mapping version strings to the per-version note tables in `notes/`, plus `BuildPatchNotes()` which flattens the currently selected note into `PatchNotesDelivered_Text` for display.
- `PatchNotesDelivered/notes/patch-*.lua` — one file per game patch version, each exporting a `PatchNotesDelivered_Notes_<version>` global table with fields like `version`, `build`, `hotfix`, `gameChangesHotfixes`, `gameChangesPatch`, and one `<class>ChangesPatch` field per WoW class. New patches get a new file here (added to both the `.toc` and `AVAILABLE_NOTES`), not by rewriting old ones. Starting with `patch-12.0.7.lua`, `gameChangesHotfixes`, `gameChangesPatch`, and `addonChanges` are arrays of `{ date, text }` entries (newest first) rather than a single `[[ ]]` string blob — see `notes/patch-template.lua`. Older files still use the single-blob format; `PatchNotesDelivered.lua`'s `NormalizeDatedEntries` handles both. Entries may also carry an optional `images` array (`{ token, path, width, height, caption? }`); reference an image inline within `text` by putting `[[img:N]]` on its own line, where `N` matches an entry's `token`. In the patch-notes window, each entry gets its own row in a date sidebar once a section has 2+ entries (see `BuildSectionItems`/`PopulateSelectedSection`); on the Patch Notes tab, non-empty `<class>ChangesPatch` fields also get their own sidebar row (labeled by class name) alongside the dated entries, instead of being appended after the main text.
- `PatchNotesDelivered/libs/` — vendored third-party Lua libs (Ace3, LibDataBroker-1.1, LibDBIcon-1.0), each a git submodule except the plain-vendored `Ace3` (see `.gitmodules`); don't hand-edit vendored libs.
- `Changelog.md` — Keep-a-Changelog-style log. Versioning is `A.B.C`: **A** = major feature bump, **B** = tracks WoW's major game version (e.g. `12` in `12.0.0`), **C** = increments on every release (hotfix/patch/minor). Update this alongside version bumps.
- `references/` — **dev-only** material, not part of the addon runtime. Currently just `references/wow-ui-source`, a submodule mirroring Blizzard's client FrameXML/SharedXML source, used to look up exact frame-template field names (e.g. `PortraitFrameTemplate`/`ButtonFrameTemplate` internals) when building UI against Blizzard's shared templates. It lives outside `PatchNotesDelivered/` deliberately — `create-release.yml` zips the whole `PatchNotesDelivered/` directory regardless of `.toc` references, so anything dev-only under there would bloat every published package even though it never loads.
- `.github/scripts/` — Python scraping/LLM-formatting scripts; **orphaned**, not part of the addon runtime. The live patch-notes-update automation now runs in an external n8n workflow (see below), not via these scripts.
- `.github/workflows/` — release/publishing/issue-promotion workflows, plus the orphaned `run-update-agent.yml`/`scrape-news.yml` (see below).

## The automation pipeline

Most day-to-day changes to `notes/*.lua` are generated by automation rather than hand-written:

1. **Patch-notes updates run in an external n8n workflow, not in this repo.** It isn't checked into `.github/` — there's no local file to read or edit; ask the user for the current workflow export if you need to inspect or change it. Triggered by a daily schedule or a `!run-auto` command in a private Discord channel, it scrapes a Blizzard news URL and its article images (both hardcoded per patch cycle in the workflow's `Set PND Variables` node, alongside the target `notes_path`), sends the scraped text plus the existing note sections and a numbered image candidate list to Claude Sonnet 5 (over SSH to a separately-hosted Claude Code VM, billed against a Claude Code subscription rather than metered API usage) asking for only the *new* hotfix/patch entries as structured `{date, text, images}` JSON (filtered to current retail — "The War Within" — discarding Classic/SoD/Hardcore content), downloads and commits any referenced images to `PatchNotesDelivered/media/<version>/`, inserts the new entries into the target notes file's `gameChangesHotfixes`/`gameChangesPatch` tables (populating the per-date `images` field described above where relevant), bumps the `.toc` iteration version and the notes file's `version`/`build`/`hotfix` fields (from the live WoW build reported by `wago.tools`), updates `Changelog.md`, and opens a PR into `dev` (`updates/auto-patch-notes-v<version>`).
2. **`.github/workflows/run-update-agent.yml`, `.github/scripts/scrape_news.py`, `.github/scripts/update_patch_notes_agent.py`** — the original GitHub Actions/Gemini implementation of the above. Still present in the repo but **orphaned** — this is not what runs; don't try to fix or invoke it for real updates.
3. **`scrape-news.yml`**: standalone scraper run, pushes raw scraped JSON/text to a timestamped branch under `.github/data/` for inspection without touching notes.
4. **`create-release.yml`** (manual): run from `main`; reads the version from the `.toc`, extracts the matching `Changelog.md` section, zips `PatchNotesDelivered/`, tags `vA.B.C`, and creates a GitHub Release.
5. **`publish-release.yml`** (manual): downloads the latest GitHub Release asset and uploads it to CurseForge and Wago/WowUp, using the version parsed out of a specific notes file (`vars.NOTES_FILE`).
6. **`check-curseforge-game-version.yml`** (manual): looks up a CurseForge game-version ID for a given patch string — useful before wiring a new WoW version into publishing.
7. **`promote-issue-to-bug.yml` / `promote-issue-to-feature.yml`**: when an allow-listed user (`vars.APPROVED_USERS`) applies the `approved` label to an issue also labeled `bug`/`feature`, a branch (`bugs/bug-...` / `features/feature-...`) is created off `dev`.

Branching model: `dev` is the integration branch (auto-update PRs and issue-promotion branches target it); `main` is release-only (tags and packages are cut from it).

## Common tasks

- **Add a new patch's notes**: create `notes/patch-X.Y.Z.lua` following the existing field structure (see any file in `notes/` as a template — note the `140`-char line-length convention marked in the file headers, matching `.vscode/settings.json`'s `editor.rulers`), add it to the `# Notes Files` list in the `.toc`, and add an entry to `AVAILABLE_NOTES` in `PatchNotesText.lua` (newest first).
- **Change how patch-notes updates are generated**: this happens in the external n8n workflow, not in this repo — there's no local script to run or edit (the `.github/scripts/*.py` versions are orphaned, see above). Ask the user for the current workflow export.
- **Bump the addon version manually**: edit `## Version:` in `PatchNotesDelivered.toc`; add a matching `## [A.B.C]` entry to `Changelog.md`.
- There is no linter/test/build command in this repo — validation is manual (load the addon in-game) or via the Lua Language Server config in `.vscode/settings.json` (Lua 5.1 runtime, WoW API annotations from the `ketho.wow-api` extension).
- **Testing the addon in-game from a fresh clone**: run `git submodule update --init --recursive` first — a plain clone/pull leaves the submodule directory `libs/LibDataBroker-1.1` empty (`Ace3`/`LibDBIcon-1.0` are plain committed files, not submodules, so they're unaffected), which causes an `Error loading .../LibDataBroker-1.1.lua`-style Lua error on load. The release workflow (`create-release.yml`) already checks out submodules recursively, so this only affects local test copies, not published packages.
- **Look up a Blizzard shared frame template's internals** (e.g. what fields/mixins `ButtonFrameTemplate` exposes): grep `references/wow-ui-source/Interface/AddOns/Blizzard_SharedXML*` — the `ketho.wow-api` extension only annotates global API functions, not template XML structure.

## Conventions

- Lua files start with a header comment block (addon name, author, file, description, license) — follow this for new files.
- Function doc comments use `--- Description:`, `--- @param:`, `--- @return:` above each function.
- Keep line length within 140 columns (see `.vscode/settings.json` rulers and the note files' explicit `Max note length` marker comments).
